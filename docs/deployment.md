# 잇플 직접 API 연결과 단일 서버 배포 준비

이 문서의 설정은 **초안이며 배포나 실서버 연결을 완료한 것이 아니다.** 기본 앱은 개발용 HTTP 서버이므로 외부에 직접 열지 않는다. 아래 구성은 단일 Linux 서버에서 Gunicorn을 `127.0.0.1`에만 열고 Caddy가 HTTPS를 받는 예시다. AWS는 필수가 아니다. 공개 전에 실제 연결 승인, 보안·알레르기 처리, 개인정보 보호와 복구 시험이 필요하다.

## 외부에서 먼저 확인할 일

1. 주최 측에 대회 팀 서비스가 직접 API와 k-skill 중 어떤 경로를 쓸 수 있는지, 개발 및 운영 환경별 기관명·IP 등록과 승인 절차를 확인한다. 개발 URL을 알고 있어도 승인 전 실제 개발 호출을 할 수 있다고 단정하지 않는다.
2. 비용과 계정의 크레딧·만료일을 확인한 뒤 단일 서버를 선택한다. 직접 API를 사용하면 서버에서 잇플로 나가는 **공인 출발 IP**가 바뀌지 않아야 하며, 발급된 IP와 실제 출발 IP가 같은지 확인해 제공처에 등록한다.
3. 서비스 호스트명과 DNS, HTTPS를 정한다. 대회 참가 등록 절차와 잇플 API 접근 승인은 별개다. 유입 인정 조건과 호스트명은 대회 담당에게 확인한다.
4. 테스트할 코드의 커밋을 팀이 정한다. 현재 PR #13은 작성 시점에 미병합이며, 작성된 배포 구성이 실제 계정에서 검증된 상태는 아니다.

## 운영 전 필수 해결 항목

- 가게의 실제 재료를 확인할 수 없으면 알레르기를 안전하거나 낮은 위험으로 추정하지 않도록 추천 담당과 수정한다. 현재 추정 로직은 이 기준을 보장하지 못한다.
- 방 링크 보유자에게 참여자 이름·알레르기 정보가 보이는 범위, 보관 기간·삭제, 공개 홍보 전 안내와 접근 통제를 팀이 결정하고 구현한다.
- 요청 남용·대량 방 생성·공유 링크 추측 등 공개 인터넷의 접근 및 요청 제한, 부하, 로그와 비밀값 노출을 별도로 점검한다. 이 예제에 완전한 남용 방지 기능이 포함된 것은 아니다.
- AI 입력의 외부 전송 범위와 가맹점 정보의 저장·캐시 허용 범위를 각 제공처에 확인한다. 자격 정보는 채팅·Git·콘솔 출력에 남기지 않는다.

## 파일과 구성

| 파일 | 역할 |
| --- | --- |
| `moim/wsgi.py` | Gunicorn WSGI 어댑터, 호스트 검사와 입력 크기 제한, `/healthz` |
| `moim/init_db.py` | 신규 배포임을 확인한 뒤 DB 파일을 최초 1회 생성 (기존 파일 덮어쓰기 불가) |
| `deploy/moim.service` | 단일 Gunicorn worker, 4개 스레드, 로컬 바인딩과 systemd 자동 재시작 |
| `deploy/Caddyfile.example` | 승인된 호스트명으로 HTTPS 종료 후 로컬 서버에 전달하는 예시 |
| `deploy/requirements.txt` | Linux 서버용 Gunicorn 의존성 |

Gunicorn은 **worker 1개**를 유지한다. 현재 참여 인원 제한에 사용하는 락은 단일 프로세스 범위이며, 여러 프로세스·서버를 안전하게 운영하는 설계가 아니다. SQLite 파일은 `/var/lib/moim/moim.sqlite3`에 둔다. 서버를 재생성해도 보관되는 디스크를 사용해야 하며, 디스크 삭제 정책도 확인한다. 운영 환경이 작동하는지와 처리량은 실제 부하 테스트로 측정한다.

## 서버 설치 순서 (설정 예시)

팀이 선택한 검증된 커밋을 `/opt/moim`에 배치하고 운영자가 소스·가상환경을 소유한다. 서비스 전용 `moim` 시스템 사용자와 그룹을 생성한다. Python 3.10 이상과 Caddy v2.10 이상을 준비한 뒤 `/opt/moim`에 가상환경을 만들고 `deploy/requirements.txt`를 설치한다. systemd 서비스가 접근할 수 있도록 `/etc/moim/moim.env`는 root 소유와 제한된 권한으로 만들고, 다음 설정을 실제 승인된 값으로 입력한다.

```text
MOIM_ALLOWED_HOST=서비스의_실제_호스트명
EATPL_INSTITUTION=발급받은_기관명
EATPL_ENV=dev
OPENROUTER_API_KEY=선택사항_서버에서만_설정
```

위 값은 설명용이며 그대로 복사해 실행하지 않는다. `MOIM_ALLOWED_HOST`에는 `https://`, 경로, 포트를 제외한 호스트만 입력한다. `EATPL_ENV`는 `dev` 또는 승인 후 `prod`를 명시한다. `MOIM_DB_PATH`는 unit 파일에서 절대 경로로 정한다. 기관명과 환경·호스트가 누락되면 WSGI 서버가 **시작을 거부**하며, 샘플 데이터로 자동 대체하지 않는다. 이것은 승인이나 실제 연결 성공 여부까지 확인하는 기능은 아니다.

서비스 최초 시작 전에 저장 폴더가 `moim` 사용자 소유이며 제한된 권한인지 확인한다. **기존 운영·테스트 서버에서 사용하던 기관명과 순번이 없다**는 것을 확인한 최초 배포에만, `/opt/moim`에서 다음 명령으로 빈 DB를 한 번 생성한다.

```bash
sudo -u moim /opt/moim/.venv/bin/python -m moim.init_db --path /var/lib/moim/moim.sqlite3 --confirm-first-deployment
```

이 명령은 파일이 이미 있으면 덮어쓰지 않는다. 서버 기동은 DB가 없거나 손상됐거나 순번 테이블을 포함한 필수 구조가 없으면 거부한다. 기존 서버 이전이나 장애 복구 시에는 새 DB를 만들지 않고 유효한 상태를 복구해야 한다. **과거 백업의 순번이 실제 발급 이력보다 뒤처졌는지는 자동으로 감지하지 못한다.** 복구 후 잇플 호출을 재개하기 전 중복 방지 방식을 제공처와 확인한다.

`deploy/moim.service`의 경로와 사용자·그룹을 확인해 systemd에 설치한다. `deploy/Caddyfile.example`의 호스트명을 동일한 값으로 바꾸어 Caddy 설정에 적용하고, `caddy validate`로 설정을 검사한다. DNS가 서버를 가리키고 80·443 포트가 도달 가능해야 인증서가 발급된다. Gunicorn의 8000 포트는 외부에 열지 않는다. systemd 시작 및 Caddy 재시작 후 `/healthz` 확인과 서버 재부팅 시 자동 기동을 시험한다.

## 실제 호출·공개 전 확인

- 제공처 승인 뒤 개발 환경에서 실제 가맹점이 표시되는지 확인한다. 예제 `/healthz`는 프로세스의 응답 여부만 나타내며 잇플 연결, DB 복구, 외부 승인 여부를 보증하지 않는다.
- 실제 장소 검색 성공, 결과 없음, 연결 실패를 각각 확인하고 샘플이 실제 결과로 나타나지 않는지 확인한다.
- 등록할 공개 호스트에서 두 기기로 같은 방에 입장해 입력·수정·삭제·새로고침·재접속을 시험한다. 다른 방의 정보가 나타나지 않는지 확인한다.
- 잇플이 반환한 상세 URL을 변경하지 않고 이용자 브라우저에서 열어, 등록 호스트와 실제 유입 출처 및 집계 여부를 검증 담당과 확인한다.
- SQLite에는 방·참여자 정보와 거래추적번호 순번이 함께 들어 있다. 별도 보관소에 접근이 제한된 일관성 있는 백업을 만들고 복구 시험을 한다. **과거 백업으로 복원하면 거래번호 순번이 되돌아갈 수 있으므로**, 복구 후 API 호출을 재개하기 전에 제공처와 중복 방지 방식을 확인한다.
- 부하·타임아웃·비용 알림과 로그, 잇플 API 오류와 서버 상태를 확인한다. 계정 무료 플랜 만료 시 서비스가 중단될 수 있으므로 담당자와 만료일을 기록한다.
