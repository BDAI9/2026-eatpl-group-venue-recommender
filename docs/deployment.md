# 잇플 직접 API 연결과 단일 서버 배포 준비

이 문서의 설정은 **초안이며 공개 배포나 실제 잇플 연결을 완료한 것이 아니다.** 기본 앱은 개발용 HTTP 서버이므로 외부에 직접 열지 않는다. 아래 구성은 단일 Linux 서버에서 Gunicorn을 `127.0.0.1`에만 열고 Caddy가 HTTPS를 받는 예시다. AWS는 필수가 아니다. 공개 전에 실제 연결 승인, 보안·알레르기 처리, 개인정보 보호와 복구 시험이 필요하다.

## 2026-11-16 서버 검증 결과

- AWS Lightsail 서울 리전의 Ubuntu 24.04 테스트 서버에 이 PR의 커밋 `1807ad7`을 받아 실행했다. 서버 커널의 보안 업데이트를 설치하고 재부팅해 새 커널 동작을 확인했다.
- 서버에서 자동 테스트 **48개와 하위 테스트 2개가 통과**했다. 별도의 임시 DB와 시험용 기관명으로 Gunicorn을 로컬에만 실행해 `/healthz`와 방 화면의 정상 응답, 허용하지 않은 호스트의 거부를 확인한 다음 시험 서버를 종료했다. 시험용 기관명으로 잇플 API는 호출하지 않았다.
- 빈 테스트 DB의 백업 파일을 만들고 SQLite 무결성을 확인했다. 실제 운영 데이터의 자동 백업, 별도 보관소, 복구 시험은 아직 필요하다.
- 서버의 고정 IPv4가 실제 외부 요청의 출발 IP와 일치함을 확인했다. 잇플 제공처에 등록할 주소는 AWS 계정의 인스턴스 네트워킹 화면에서 확인한다.
- 실제 기관명·IP 승인, 실제 가맹점 검색, Caddy·공개 HTTPS, 도메인, 공동 사용 및 장애·부하 시험은 아직 확인하지 않았다. 웹 포트는 공개하지 않았고 SSH는 Lightsail 브라우저 연결로 제한했다.

### 잇플 연결 경로 재확인

위 서버 시험과 별도로 2026-11-16에 K-Skill의 공개 프록시를 개인 개발 환경에서 호출했다. 기관명 입력 없이 을지로 카페 검색에서 실제 잇플 가맹점, 상세 링크와 `upstream.provider=bccard-eatpl`을 확인했다. 로컬 앱의 방 생성 → 참여자 입력 → 추천 처리에서도 을지로 카페·식당·술집 각각 실제 결과 10건과 상세 링크를 확인했다. 로컬 브라우저에서 방 생성·조건 저장·카페 추천 표시를 시험하고 반환된 상세 URL을 별도로 열어 잇플 가게 페이지를 확인했다. 공개 서버에서의 전체 흐름과 브라우저 간 유입 집계는 아직 시험하지 않았다. 이는 **직접 제휴 API에 우리 서버 IP를 등록하지 않은 상태에서도 공개 프록시를 통한 시험 조회가 가능했다**는 뜻이다.

직접 API는 제휴 기관명과 호출 서버의 IP 등록이 필요한 별도 경로다. K-Skill 공개 프록시는 운영자가 제공하는 중계 경로이며, 개인 이용자의 시험 호출과 별도로 실제 운영 요건은 주최 측에 확인한다. K-Skill 지침에도 운영 전 승인·노출 문구 검수 안내가 있다. [K-Skill 연결 지침](https://github.com/NomaDamas/k-skill/blob/main/bccard-eatpl-search/instruction.md)

공모전 안내는 K-Skill을 서비스에 연결하고, 응답의 잇플 상세 주소를 변형하지 않은 채 이용자의 웹 브라우저로 열도록 명시한다. 등록한 호스트명과 실제 유입 경로가 다르거나 중간 링크를 거치면 집계되지 않을 수 있다. 동작하는 서비스가 필요하며 등록 도메인은 12월 3일 전까지 한 번 변경할 수 있다. [공식 참가 신청 안내](https://edu.bccard.ai/static/contest/apply.html)

Lightsail의 임시 웹 주소는 별도 Distribution이 필요하며 인스턴스 요금 외에 추가 비용이 생긴다. 이를 사용할 경우 방별 정보가 공유 캐시에 저장되지 않도록 하고, 브라우저부터 원본 서버까지 HTTPS, 허용 호스트와 요청 전달을 검증해야 한다. 임시 웹 주소의 인증서가 원본 인스턴스에 자동 설치되는 것은 아니다. [웹 주소 안내](https://docs.aws.amazon.com/lightsail/latest/userguide/amazon-lightsail-web-addresses.html), [Distribution 원본 설정](https://docs.aws.amazon.com/lightsail/latest/userguide/amazon-lightsail-distribution-origins.html)

2026-11-16 현재 `jj-moim.amazonlightsail.com`을 생성해 `jj-moim-distribution`에 연결했다. Distribution은 캐시 없음과 HTTPS 전용 원본 연결로 설정했지만, **서버 원본 인증서와 외부 웹 연결은 아직 완료되지 않아 이 주소로 앱을 사용할 수 없다.** 서버에 커밋 `681e64e`를 설치하고 K-Skill 설정으로 로컬 서비스 및 내부 HTTP 방 생성 → 참여 → 실제 카페 10건 추천을 검증했다. 서비스는 `127.0.0.1:8000`에만 바인딩돼 있다. 서버 월 $7, Distribution 월 $2.50이며 트래픽 초과 요금 등은 별도다.

## 외부에서 먼저 확인할 일

1. 주최 측에 K-Skill 공개 프록시를 이용하는 대회 서비스의 별도 운영 승인과 노출 문구를 확인한다. 직접 API를 택할 경우 개발 및 운영 환경별 기관명·IP 등록과 승인 절차를 확인한다.
2. 비용과 계정의 크레딧·만료일을 확인한 뒤 단일 서버를 선택한다. 직접 API를 사용하면 서버에서 잇플로 나가는 **공인 출발 IP**가 바뀌지 않아야 하며, 발급된 IP와 실제 출발 IP가 같은지 확인해 제공처에 등록한다.
3. 서비스 호스트명과 DNS, HTTPS를 정한다. 대회 참가 등록 절차와 잇플 API 접근 승인은 별개다. 유입 인정 조건과 호스트명은 대회 담당에게 확인한다.
4. 테스트할 코드의 커밋을 팀이 정한다. PR #13은 dev에 반영됐으며, 이 배포 준비 변경은 PR #14에서 검토 중이다. 위에 열거한 검증과 공개 배포 검증을 구분한다.

## 운영 전 필수 해결 항목

- 가게의 실제 재료를 확인할 수 없으면 알레르기를 안전하거나 낮은 위험으로 추정하지 않도록 추천 담당과 수정한다. 현재 추정 로직은 이 기준을 보장하지 못한다.
- 방 링크 보유자에게 참여자 이름·알레르기 정보가 보이는 범위, 보관 기간·삭제, 공개 홍보 전 안내와 접근 통제를 팀이 결정하고 구현한다.
- 요청 남용·대량 방 생성·공유 링크 추측 등 공개 인터넷의 접근 및 요청 제한, 부하, 로그와 비밀값 노출을 별도로 점검한다. 이 예제에 완전한 남용 방지 기능이 포함된 것은 아니다.
- AI 입력의 외부 전송 범위와 가맹점 정보의 저장·캐시 허용 범위를 각 제공처에 확인한다. 자격 정보는 채팅·Git·콘솔 출력에 남기지 않는다.

## 파일과 구성

| 파일 | 역할 |
| --- | --- |
| `moim/wsgi.py` | Gunicorn WSGI 어댑터, 호스트 검사와 입력 크기 제한, `/healthz` |
| `moim/init_db.py` | 신규 배포임을 확인한 뒤 DB 파일을 최초 1회 생성 (기존 파일 덮어쓰기 불가) |
| `deploy/moim.service` | 단일 Gunicorn worker, 4개 스레드, 로컬 바인딩과 systemd 자동 재시작 |
| `deploy/Caddyfile.example` | 승인된 호스트명으로 HTTPS 종료 후 로컬 서버에 전달하는 예시 |
| `deploy/requirements.txt` | Linux 서버용 Gunicorn 의존성 |

Gunicorn은 **worker 1개**를 유지한다. 현재 참여 인원 제한에 사용하는 락은 단일 프로세스 범위이며, 여러 프로세스·서버를 안전하게 운영하는 설계가 아니다. SQLite 파일은 `/var/lib/moim/moim.sqlite3`에 둔다. 서버를 재생성해도 보관되는 디스크를 사용해야 하며, 디스크 삭제 정책도 확인한다. 운영 환경이 작동하는지와 처리량은 실제 부하 테스트로 측정한다.

## 서버 설치 순서 (설정 예시)

팀이 선택한 검증된 커밋을 `/opt/moim`에 배치하고 운영자가 소스·가상환경을 소유한다. 서비스 전용 `moim` 시스템 사용자와 그룹을 생성한다. Python 3.10 이상과 Caddy v2.10 이상을 준비한 뒤 `/opt/moim`에 가상환경을 만들고 `deploy/requirements.txt`를 설치한다. systemd 서비스가 접근할 수 있도록 `/etc/moim/moim.env`는 root 소유와 제한된 권한으로 만들고, 다음 설정을 실제 승인된 값으로 입력한다.

```text
MOIM_ALLOWED_HOST=서비스의_실제_호스트명
EATPL_SOURCE=direct
EATPL_INSTITUTION=발급받은_기관명
EATPL_ENV=dev
OPENROUTER_API_KEY=선택사항_서버에서만_설정
```

위 값은 직접 API용 설명이며 그대로 복사해 실행하지 않는다. `MOIM_ALLOWED_HOST`에는 `https://`, 경로, 포트를 제외한 호스트만 입력한다. 직접 API의 `EATPL_ENV`는 `dev` 또는 승인 후 `prod`를 명시한다. K-Skill 프록시는 `EATPL_SOURCE=kskill`을 명시하며 직접 API 기관명과 환경 설정을 사용하지 않는다. `MOIM_DB_PATH`는 unit 파일에서 절대 경로로 정한다. 필요한 호스트·DB나 직접 API 설정이 빠지면 WSGI 서버가 **시작을 거부**하며, 샘플 데이터로 자동 대체하지 않는다. 이것은 승인이나 실제 연결 성공 여부까지 확인하는 기능은 아니다.

서비스 최초 시작 전에 저장 폴더가 `moim` 사용자 소유이며 제한된 권한인지 확인한다. **기존 운영·테스트 서버에서 사용하던 기관명과 순번이 없다**는 것을 확인한 최초 배포에만, `/opt/moim`에서 다음 명령으로 빈 DB를 한 번 생성한다.

```bash
sudo -u moim /opt/moim/.venv/bin/python -m moim.init_db --path /var/lib/moim/moim.sqlite3 --confirm-first-deployment
```

이 명령은 파일이 이미 있으면 덮어쓰지 않는다. 서버 기동은 DB가 없거나 손상됐거나 순번 테이블을 포함한 필수 구조가 없으면 거부한다. 기존 서버 이전이나 장애 복구 시에는 새 DB를 만들지 않고 유효한 상태를 복구해야 한다. **과거 백업의 순번이 실제 발급 이력보다 뒤처졌는지는 자동으로 감지하지 못한다.** 복구 후 잇플 호출을 재개하기 전 중복 방지 방식을 제공처와 확인한다.

`deploy/moim.service`의 경로와 사용자·그룹을 확인해 systemd에 설치한다. `deploy/Caddyfile.example`의 호스트명을 동일한 값으로 바꾸어 Caddy 설정에 적용하고, `caddy validate`로 설정을 검사한다. DNS가 서버를 가리키고 80·443 포트가 도달 가능해야 인증서가 발급된다. Gunicorn의 8000 포트는 외부에 열지 않는다. systemd 시작 및 Caddy 재시작 후 `/healthz` 확인과 서버 재부팅 시 자동 기동을 시험한다.

## 실제 호출·공개 전 확인

- 제공처 승인 뒤 개발 환경에서 실제 가맹점이 표시되는지 확인한다. 예제 `/healthz`는 프로세스의 응답 여부만 나타내며 잇플 연결, DB 복구, 외부 승인 여부를 보증하지 않는다.
- 실제 장소 검색 성공, 결과 없음, 연결 실패를 각각 확인하고 샘플이 실제 결과로 나타나지 않는지 확인한다.
- 등록할 공개 호스트에서 두 기기로 같은 방에 입장해 입력·수정·삭제·새로고침·재접속을 시험한다. 다른 방의 정보가 나타나지 않는지 확인한다.
- 잇플이 반환한 상세 URL을 변경하지 않고 이용자 브라우저에서 열어, 등록 호스트와 실제 유입 출처 및 집계 여부를 검증 담당과 확인한다.
- SQLite에는 방·참여자 정보와 거래추적번호 순번이 함께 들어 있다. 별도 보관소에 접근이 제한된 일관성 있는 백업을 만들고 복구 시험을 한다. **과거 백업으로 복원하면 거래번호 순번이 되돌아갈 수 있으므로**, 복구 후 API 호출을 재개하기 전에 제공처와 중복 방지 방식을 확인한다.
- 부하·타임아웃·비용 알림과 로그, 잇플 API 오류와 서버 상태를 확인한다. 계정 무료 플랜 만료 시 서비스가 중단될 수 있으므로 담당자와 만료일을 기록한다.
