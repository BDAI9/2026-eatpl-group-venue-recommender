# 잇플 연동·배포 진행표

기준: PR #13으로 `dev`에 반영된 모임 앱을 바탕으로 한 배포 준비. 실제 제휴 API와 외부 서버 연동 완료를 뜻하지 않는다.

## 지금 정해진 범위

- 현재 모임 앱은 `EATPL_INSTITUTION`을 설정하면 직접 제휴 API를 사용하며, 비어 있으면 가상 샘플을 사용한다. 기존 공개 프록시는 이 앱의 실제 조회 경로가 아니다.
- 개발과 운영 서버는 `EATPL_ENV`로 선택한다. 기관명 발급·출발 공인 IP 등록이 되어야 개발 서버도 확인할 수 있고, 운영 전환 조건은 제공처에 확인한다.
- API 정의서의 기관명과 거래추적번호는 OpenRouter 키와 별개다. 실제 발급 정보는 채팅·저장소·로그에 쓰지 않는다.
- 대회 안내의 k-skill 경로도 있으므로 직접 API 등록 조건을 모든 경로에 일률적으로 적용하지 않는다.
- 2026-11-16 AWS Lightsail 서울 리전에 1GB 인스턴스(월 $7 플랜)와 고정 IPv4를 생성했다. 인스턴스의 실제 IPv4 출발 주소가 고정 IP와 일치하는 것을 확인했다. 연결된 고정 IP는 콘솔에서 확인하며, IP 할당은 잇플의 등록·승인을 뜻하지 않는다.
- SSH는 Lightsail 브라우저 콘솔만 허용하고 HTTP 포트는 아직 닫아 뒀다. AWS의 Linux 커널 보안 경고에 따라 패치 설치를 시작했으나 완료·재부팅 검증은 아직 확인하지 못했다. 웹 앱, 도메인, HTTPS와 실제 API 연결은 미완료다.
- 도메인은 미정이며 임시 Lightsail 주소를 우선 검토한다. 해당 주소를 쓰려면 배포망과 별도 요금·원본 캐시 정책, 공모전 등록 가능 여부를 확인해야 한다.

## 우선순위와 확인할 일

1. **운영진 문의:** 기관명 발급 신청, 개발·운영 각각의 출발 IP 허용, 팀 서비스의 k-skill 허용 여부, 비용과 처리 기간. 등록 전 기관명이 없는 상태에서는 직접 API의 실호출을 완료할 수 없다.
2. **계정·비용:** AWS 계정의 플랜·크레딧·만료일과 Lightsail 사용 가능 여부를 확인하고, IPv4 서버·디스크·백업·도메인 비용을 추산한다. Lightsail은 인스턴스에 고정 IPv4를 연결할 수 있으나 IPv6 전용 플랜에는 연결할 수 없다. 무료 혜택과 견적을 확인하기 전 리소스를 만들지 않는다.
3. **주소:** 서비스 등록 담당과 공개 도메인/서브도메인 사용 가능 여부를 확인하고 HTTPS를 준비한다. IP 등록은 사용자가 아닌 앱이 잇플로 요청을 보내는 출발 IP 기준이다.
4. **실제 조회:** 발급 후 개발 서버부터 테스트한다. 가상 샘플이 아닌 실제 응답과 원문 상세 링크, 검색 0건·실패 안내를 확인한다. 운영 전환은 별도 승인 후에만 진행한다.
5. **모임 데이터:** 방과 참여자 및 거래추적번호 순번이 SQLite에 함께 저장된다. 서버 재시작 후 유지, 정기 백업과 복구를 확인한다. 같은 기관의 거래번호를 여러 서버에서 별도 DB로 만들지 않는다.
6. **등록:** 공개 주소에서 서로 다른 두 기기로 방 참여·재접속과 실제 잇플 상세 이동을 확인하고, 신청 담당자에게 등록 도메인을 전달한다. 실제 유입 집계는 주최 측 등록 완료와 공식 조건으로 확인한다.

## 준비된 점검 도구

기본 점검은 환경 변수 설정 여부만 확인하며 외부에 요청을 보내지 않는다.

```bash
python -m moim.eatpl_probe
```

실제 조회는 제공처의 개발 서버 접근 및 출발 IP 허용 후, 서버에서 발급된 `EATPL_INSTITUTION` 환경 변수를 안전하게 설정하고 아래 예시처럼 명시적으로 실행한다. `--db`는 앱과 동일한 **기존 DB**여야 한다. 기관명·거래추적번호는 출력하지 않고, 실제 조회가 실패하면 가상 데이터로 대체하지 않는다. 이 도구는 `.env`를 자동으로 읽지 않는다.

```bash
python -m moim.eatpl_probe --live --environment dev --location 강남 --db /var/lib/moim/moim.sqlite3
```

운영 환경은 별도 승인 후에만 `--environment prod`로 선택한다. 다른 DB를 만들어 독립적으로 진단하면 거래추적번호가 중복될 수 있으므로 반드시 실제 앱과 같은 DB를 쓴다.

백업은 이미 존재하는 DB를 읽어 일관된 스냅샷을 새 파일로 만든다. 아래는 경로 예시이며 백업 폴더는 미리 만들고 참여자 정보가 노출되지 않도록 접근을 제한한다. 기존 대상 파일을 덮어쓰지 않는다.

```bash
python -m moim.backup /var/lib/moim/moim.sqlite3 /private-backups/moim-2026-11-16.sqlite3
```

## 공개 전 팀 협의가 필요한 항목

- 현 앱은 이름·알레르기 조건을 링크 보유자에게 보여 줄 수 있다. 공유 범위와 삭제·보관 방식을 검토한다.
- AI의 알레르기 추정과 과거 캐시는 위험 판단에 사용하지 않는다. 실제 재료 정보가 없어도 업종·상호 규칙에 의한 판단에는 한계가 있으므로 추천 담당과 사용자 안내를 검토한다.
- 장소 데이터 이용 조건과 실제 좌표의 출처·변환은 별도 확인한다. 핀 위치를 확인하기 전 거리나 지도 정확성을 보장하지 않는다.
- 서비스와 데이터에 대한 네트워크 접근, 요청 남용 및 재시작 시 복구를 점검한다. 로컬 테스트 서버를 인터넷에 그대로 노출하지 않는다.

## 거래추적번호와 복구

SQLite의 `trace_sequence`를 오래된 백업으로 되돌리면 이미 사용된 번호를 다시 발급할 수 있다. 자동 복원하거나 다른 서버에서 별도 순번을 만들지 않는다. 복구가 필요하면 호출을 중단하고 실제 발급된 순번 상한과 운영진의 처리 방법을 먼저 확인한다. 별도 안전한 복구 절차가 준비되지 않았다면 같은 기관의 호출을 완전히 중단하고 KST 날짜가 바뀐 뒤 재개하는 방안을 운영진과 확인한다.
